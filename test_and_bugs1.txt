PARTE 1 - SOLICITUD DEL USUARIO (QUÉ SE PIDIÓ)
======================================================================

Se solicita revisar e implementar los siguientes puntos prioritarios
para dejar el flujo de emisión técnicamente sólido antes del hito de
conexión con API real de emisión de boletas.

Importante: La validación/bloqueo por monto sobre $180.000 fue
deshabilitada intencionalmente. La decisión funcional es permitir que
el usuario tenga libertad de emisión y luego mostrar un disclaimer o
advertencia clara en la interfaz. No considerar ese punto como bloqueo
técnico crítico.

Orden de prioridad solicitado:
  1. Idempotency-key
  2. Manejo seguro de folios
  3. Estado pendiente_confirmacion
  4. Timeout frontend/backend
  5. Audit log / emission_attempts
  6. Emitido_por
  7. Polling/consulta SII
  8. beforeunload guard
  9. Mock SII más realista

PARTE 2 - HALLAZGOS POR PUNTO
======================================================================

1. IDEMPOTENCY-KEY
-------------------
Estado actual: NO IMPLEMENTADO

Qué existe hoy:
- Botón "Emitir" se deshabilita en frontend (estado emitiendo=true)
- Backend verifica yaEmitidas por propuesta_id contra boletas_emitidas
- Índice único parcial en DB: idx_boletas_propuesta_unica_vigente
- consume_next_folio usa SELECT ... FOR UPDATE (atómico)

Qué falta:
- No hay idempotency-key por request (solo por propuesta_id)
- No se puede reintentar un batch de forma segura tras timeout
- Si el frontend reintenta tras timeout, se crea un NUEVO batch
- Si consume_next_folio ya ejecutó y luego falla el INSERT, el folio
  se pierde y el reintento consume OTRO folio
- catch {} en yaEmitidas traga errores silenciosamente

Archivos involucrados:
- src/app/api/intermediaria/emitir-lote/route.ts
- src/app/api/intermediaria/emitir-boleta/route.ts
- src/app/(app)/escritorio/v5/EmitirTabContent.tsx
- Nueva migración SQL: tabla emision_idempotency

Solución propuesta:
- Frontend genera crypto.randomUUID() como X-Idempotency-Key
- Backend almacena response por key; si se repite, devuelve el mismo
- TTL 24hs con limpieza automática
- Cubre doble click, timeout, refresh, reintento


2. MANEJO SEGURO DE FOLIOS
---------------------------
Estado actual: CON RIESGO

Qué existe hoy:
- consume_next_folio es atómico con FOR UPDATE
- Folio se retorna ANTES del INSERT en boletas_emitidas

Qué falta:
- Si consume_next_folio se ejecuta y luego el INSERT falla, el folio
  queda consumido y NO se puede recuperar
- Si SII rechaza después de consumir folio, el folio se pierde
- En producción con CAFs reales, folios perdidos = dinero perdido
- No existe función release_folio

Archivos involucrados:
- supabase/migrations/20260415_boletas_sii_mock.sql (consume_next_folio)
- src/app/api/intermediaria/emitir-lote/route.ts
- src/app/api/intermediaria/emitir-boleta/route.ts

Solución propuesta (Opción A + B combinadas):
- Reordenar flujo: validar todo → enviar al SII → si SII acepta →
  consumir folio → INSERT
- Agregar release_folio() para safety net si INSERT falla pese a todo
- Si el SII rechaza, NO se consume folio


3. ESTADO PENDIENTE_CONFIRMACION
---------------------------------
Estado actual: NO IMPLEMENTADO

Qué existe hoy:
- boletas_emitidas.estado CHECK constraint solo permite:
  aceptado, aceptado_reparos, rechazado, anulada

Qué falta:
- No hay estado para emisiones donde no se sabe el resultado
- Si hay timeout entre SII y la app, no hay cómo marcar el caso
- Pendientes-emision trata todo como binario (emitido o no)
- Usuario no puede identificar boletas "en duda"

Archivos involucrados:
- Nueva migración SQL (ALTER CHECK constraint)
- src/app/api/intermediaria/emitir-lote/route.ts
- src/app/api/intermediaria/emitir-boleta/route.ts
- src/app/api/intermediaria/pendientes-emision/route.ts
- src/app/(app)/escritorio/v5/EmitirTabContent.tsx (UI badge)
- src/lib/database.types.ts (tipos)

Solución propuesta:
- Agregar 'pendiente_confirmacion' al CHECK de estado
- Usarlo cuando timeout/f inserción falla después de consumir folio
- Excluir items en este estado de "pendientes para emitir"
- Mostrar badge naranja + botón "Consultar estado" en UI


4. TIMEOUT FRONTEND Y BACKEND
------------------------------
Estado actual: NO IMPLEMENTADO

Qué existe hoy:
- Frontend fetch no tiene timeout explícito
- Backend no tiene timeout individual por item
- El usuario puede quedar en "Emitiendo..." indefinidamente si la
  request se cuelga

Qué falta:
- Timeout en fetch del frontend (AbortController con 30s)
- Timeout controlado por item en backend
- Mensaje claro al usuario si el proceso queda inconcluso
- Si hay timeout, marcar estado como pendiente_confirmacion

Archivos involucrados:
- src/app/(app)/escritorio/v5/EmitirTabContent.tsx
- src/app/api/intermediaria/emitir-lote/route.ts

Solución propuesta:
- AbortController con timeout de 30s en frontend
- Promise.race con timeout de 10s por item en backend
- Si timeout después de consumir folio → pendiente_confirmacion

======================================================================
PARTE 8 - RESUMEN EJECUTIVO
======================================================================

Para pruebas internas (mock SII actual):
  Riesgo BAJO. Los folios son ficticios, el mock siempre acepta,
  y el índice único de DB evita duplicados graves. El flujo es
  funcional para desarrollo y testing.

Para producción real (SII verdadero):
  Los puntos 1 (idempotency-key) y 2 (folios seguros) son
  IMPOSTERGABLES antes de conectar con API real. Sin ellos:
  - Cada reintento tras error puede duplicar boletas o quemar folios
  - Los folios perdidos son dinero perdido (los CAFs se compran al SII)
  - No hay trazabilidad de quién emitió ni de intentos fallidos

  Los puntos 3 (pendiente_confirmacion), 4 (timeout), 5 (audit log)
  y 6 (emitido_por) son ALTAMENTE RECOMENDADOS antes de producción
  para garantizar operación segura y auditable.

  Los puntos 7 (polling), 8 (beforeunload) y 9 (mock realista) son
  MEJORAS que pueden implementarse progresivamente.
